# BinKeeper browser and UX review, 2026-09-24

## Review basis

Target: the owner-facing BinKeeper catalog, photo drop, registration form, and existing-bin management page. The owner uses these pages to find a bin, check its location and contents, upload a photo, and review a proposed label. The baseline was clean `master` at `4692fa8`. The owner requested a UIPass run because the UI is difficult to use.

The browser ran against [`scripts/uipass_fixture.py`](../../scripts/uipass_fixture.py) and [`.uipass.yaml`](../../.uipass.yaml), not the production writer. The fixture serves synthetic passports and a pending review through the real templates, accepts only safe HTTP methods, and removes the database URL before starting. No owner bin data, model call, printer action, or inventory mutation entered the run. The frozen tailnet endpoint was read once only to check whether the misleading copy was also live; it still said “local vision model,” “no cloud upload,” and “no network egress” before this change.

| Surface | Review depth | User task and evidence |

| Catalog populated and no-match states, `/bins/` | Deep | Find a bin and reach its recorded contents/site; browser screenshots at 320, 390, and 1280 CSS px. |

## Verdict

**SHIP_WITH_NOTES, medium confidence for the inspected pages.** The baseline had three blocking narrow-screen overflow findings and misleading disclosure of photo processing. This change removes both, plus the catalog's wasted desktop space and hidden phone navigation. The final UIPass run completed all 15 selected cases with zero findings or warnings. Actual uploads, registration, stash decisions, and live tailnet behavior after deployment remain outside this browser run.

## Claims and observed behavior

- **Contradicted in the baseline:** The photo form said the vision model was local and there was no cloud upload. The configured default is OpenRouter, which receives a downscaled inference image and prompt. The original is stored in the local vault on form submission, before any label or registration confirmation. The [photo drop handler](../../src/binkeeper/bin_photo_web/__init__.py) and [vision selection](../../src/binkeeper/bin_vision.py) establish this path. The baseline's shared help and footer repeated the false no-cloud claim. The proposed copy now describes the configured provider and the storage timing.
- **Verified in the synthetic browser:** At 320 CSS px, the baseline file inputs extended the document to 372 CSS px on the photo, register, and manage pages. The final run kept all three within the viewport.
- **Observed in screenshots:** On desktop, the baseline's four catalog stats formed a tall right column, placing search and bin results much lower. Empty photo frames occupied most of each card. On the narrow screen, “Stash” was outside the visible navigation row. The revised layout brings search and bin details forward and shows all four navigation links.

## Resolved findings

1. **SERIOUS — misleading photo-processing disclosure.** A user deciding whether to submit a private photo was told that analysis was local and that no cloud upload occurred. The default provider can send a downscaled image and prompt to OpenRouter, and the original photo is already stored when the form returns. Evidence: baseline [photo screenshot](photo-narrow-before.png), production page copy, source trace above. Fix: describe local original storage, possible configured cloud analysis, and the later registration/printing confirmation in the form, help, and footer. A focused test guards the disclosure.
2. **BLOCKER at 320 px — file input overflow.** The browser's native file input forced 52 CSS px of horizontal document overflow on three high-use forms, making the right edge and controls hard to reach. Evidence: [baseline verdict](uipass-before.json) and [photo screenshot](photo-narrow-before.png). Fix: give file inputs a zero minimum width and constrain them to the form width. The [final photo screenshot](photo-narrow-after.png) shows the control contained.
3. **SERIOUS — primary catalog work buried on desktop.** Four stats stacked vertically beside the title, leaving a large empty region while search and bin contents began far below the header. Missing-photo frames then consumed another large block before the contents. Evidence: [before](catalog-desktop-before.png) and [after](catalog-desktop-after.png) screenshots. Fix: put stats in a full-width row and make missing-photo placeholders compact while preserving the full image frame for real photos.
4. **SERIOUS — “Stash” hidden on a narrow phone.** The navigation row scrolled horizontally with no visible cue; the fourth task entry was offscreen. Evidence: baseline narrow screenshots and [final narrow catalog](catalog-narrow-after.png). Fix: use two visible navigation rows below 480 CSS px.
5. **MINOR — invalid accessible labels on generic catalog containers.** Axe flagged 18 `aria-prohibited-attr` warnings in the baseline because generic `div` elements had `aria-label` without a suitable role. Fix: use `role="group"` for meaningful groups and remove the redundant label on the visible pending-review stat. The final run reported none.

## Accessibility, responsiveness, and states

UIPass checked selected axe rules, overflow, page errors, and console errors in every declared case. Its baseline recorded three blocking overflow findings and 23 axe items requiring review; the final run recorded none. The revised phone tabs and file controls were visually inspected at 320 CSS px. The no-match catalog state was included. Keyboard completion, screen-reader announcements during real submissions, actual photos, and permission or service errors were not exercised; a passing mechanical verdict does not certify those workflows.
